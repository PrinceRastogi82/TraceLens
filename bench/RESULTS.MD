## Batcher (server coalesces requests into one insert)

Run on 2026-11-19. Command: `npx tsx ..\bench\ingest-bench.ts 4000 128 1` (4000 requests x 8 spans = 32,000 spans, concurrency 128). Server restarted per config with `BATCH_ROWS` / `BATCH_WAIT_MS` (default 2000 rows / 50 ms). `BATCH_ROWS=1` flushes every request on its own. Same laptop and setup as above.

| Config | spans/s (3 runs) | median spans/s | median p50 / p95 / p99 ms |
|---|---|---|---|
| No batching (BATCH_ROWS=1) | 4337, 4516, 4541 | 4516 | 219.9 / 270.7 / 319.4 |
| 2000 rows / 50 ms | 6901, 7195, 7252 | 7195 | 127.9 / 201.3 / 253.8 |

All 6 runs: sent = inserted = counted in ClickHouse = 32,000, 0 dropped.

Earlier single runs (not repeated, so not results): batch size 10 / 50 / 100 traces per request at concurrency 4 gave 1766 / 8673 / 15683 spans/s; 2000 rows / 10 ms gave 4975 spans/s at concurrency 128.

Not measured: latency overhead at low load (a lone request can wait up to 50 ms), memory use, ClickHouse part counts, other BATCH_ROWS / BATCH_WAIT_MS values.


## Trace-by-ID lookup (bloom index on trace_id)

Run on 2026-11-19. Command: `npx tsx ..\bench\fetch-bench.ts 200` (3 runs). Table had 1,920,002 rows (about 235 granules), all generated by `ingest-bench.ts` (8 spans per trace, services `bench-*`). Each run looks up 200 random traces with skip indexes ON and a different 200 with `use_skip_indexes=0`, one at a time, after 10 warm-up lookups. Every lookup returned exactly 8 spans (0 wrong).

| Skip indexes | p50 ms (3 runs) | median p50 / p95 / p99 ms | rows read per lookup |
|---|---|---|---|
| ON | 10.2, 9.8, 9.9 | 9.9 / 11.4 / 12.8 | 57,344 (7 granules) |
| OFF | 17.0, 16.6, 17.0 | 17.0 / 18.5 / 19.5 | 1,920,002 (whole table) |

The index cut rows read by about 33x but p50 latency by only about 1.7x. Likely reasons (not tested): the data was just written and sits in cache, a full column scan of 1.9M rows is fast, and each lookup has a fixed cost of several ms (HTTP, query setup). The latency gap may grow on a bigger or cold table; that was not measured.

Limits: synthetic traces, one table size, one lookup at a time (no concurrent readers), client-side latency over HTTP, `use_skip_indexes` is the setting used to switch the index off.


## Method and limits (applies to all runs above)

- Batcher runs: 2026-11-19. Node v24.13.0, ClickHouse 26.3.57 in Docker Desktop, table from `schema/001_spans.sql`. Git commit: not recorded yet (repo not created); add it once the repo exists.
- Data is generated, not real: 8 spans per trace across 5 services (`bench-*`), 1 attribute per span, JSON over HTTP, no gzip. Real traces carry more attributes, so real rows are larger and throughput will differ. Do not quote these numbers as production throughput.
- Client, ingest server and ClickHouse share one laptop and its CPU.
- Latency is measured by the client: from sending a request until the full response is read (includes the ClickHouse insert, and the batch wait when batching is on). p50/p95/p99 are percentiles over all requests in one run.
- Loss check: every run uses a random 8-hex run ID as the trace_id prefix. After the run the script counts rows with that prefix directly in ClickHouse and compares to spans sent. It also prints the server's own counters (inserted delta, dropped this run). A mismatch exits with an error.
- Medians are over 3 runs per config unless a row says "single run".
